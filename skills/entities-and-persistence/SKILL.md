# Entities and Persistence

Kinotic persistence is code-first: entities are plain TypeScript classes with
decorators, and typed repository classes are generated from them. Exact decorator
signatures and the full repository API are in `references/decorators.md`. Deeper
documentation: <https://kinotic.ai/apps/persistence/overview>.

## Where things live

`.config/kinotic.config.ts` names the directories (`entitiesPaths[].path` for entity
classes, `repositoryPath` for generated repositories). In the standard scaffold that is
`packages/domain/model` and `packages/domain/repositories` — but always trust the
config file in the repository.

## Defining an entity

```typescript
import { Entity, AutoGeneratedId, NotNull, Text, Precision, PrecisionType, MultiTenancyType } from '@kinotic-ai/persistence'

@Entity(MultiTenancyType.NONE)
export class Person {
    @AutoGeneratedId
    id: string | null = null

    @NotNull
    firstName: string = ''

    @NotNull
    lastName: string = ''

    @Text
    bio: string = ''

    @Precision(PrecisionType.SHORT)
    age: number = 0
}
```

Rules:

- **Exactly one id field**: `@AutoGeneratedId` on `id: string | null = null` (server
  assigns on save) or `@Id` on a `string = ''` field you populate yourself.
- Give properties defaults so entities serialize round-trip cleanly; optional (`?`) and
  definitely-assigned (`!`) properties are also accepted.
- Strings are exact-match (keyword) indexed unless marked `@Text` (full-text). Numbers
  default to 32-bit INT unless `@Precision(...)` says otherwise.
- Decorators are compile-time markers read from the source; entity classes stay plain
  data. One exception: with `validate: true` in `.config/kinotic.config.ts`, the
  generated repository enforces the decorators client-side before a save/update
  reaches the server (the scaffold ships `validate: false`, so the server does the
  rejecting).
- Browsers cannot parse the decorators, so a Vite UI that uses an entity class as a value
  (`new Todo()`) compiles them with a plugin in its `vite.config.ts`; the `frontend` skill
  has it.
- Dates are `string` fields holding ISO-8601 values, decorated with `@DateTime`
  (`createdAt: string = new Date().toISOString()`). The generator rejects a `Date` property.
- For time-series data use `@Entity(MultiTenancyType.NONE, EntityType.STREAM)` with one
  `@TimeReference` `@DateTime` timestamp field.

## The change workflow

1. Create or edit entity classes under the configured entities path.
2. Run `bun run generate` from the project root — regenerates
   `generated/Base<Entity>Repository` for every entity, creates `<Entity>Repository`
   (once) for new ones, and writes each entity's schema to
   `.config/c3/entities/<namespace>.<name>.json` (named queries to
   `.config/c3/queries/<RepositoryName>.json`). Local only; no server connection.
3. **Export the entity and its repository from the domain package's `index.ts`.**
   Generation does not touch the barrel, and nothing else in the workspace can import
   what is not exported from it:

   ```typescript
   // packages/domain/index.ts
   export * from './model/Person.js'
   export * from './repositories/PersonRepository.js'
   ```
4. Run `bun run type-check`, then commit and push everything generate produced — the
   entity sources, the generated repository classes, and `.config/c3`. Keep `.config/c3`
   in git: it is a generation artifact rather than a server input, but committing it is
   what makes a schema change visible in a diff. Never run `kinotic login` or
   `kinotic sync` yourself.

Pushing to the default branch is what reaches the server: the deployment's build VM runs
`kinotic sync` over the checkout, which regenerates, pushes the entity definitions and
named queries, and applies pending migrations. A commit that does not compile fails
there and never reaches the running services — so `bun run type-check` locally before
pushing, and confirm the outcome with `Project Service Find Deployment` (the `deploying`
skill).

Only the `Base*` classes are regenerated; the `<Entity>Repository` subclass is created
once and never overwritten, so custom code (like named queries) belongs there.

## What publishing an entity means

The deployment's sync publishes every entity it introduces, which is what creates its
backing storage — so a pushed entity is ready for data operations with no manual step.
What matters is the consequence: a **published definition is additive-only**. A later
push may add new fields and the mapping updates in place. Anything else goes wrong, each
in its own way: changing a field's type is rejected by the store and fails the sync step,
so the deployment; switching a table to a stream is refused by the platform; and renaming
a field is not refused at all — the new field is added and the old one stays mapped, with
its data, so the rename silently leaves a stale field behind. There are two ways forward:

- **Un-publish and re-publish** from the portal's **Entities** page. This **deletes the
  underlying index with all its data**. Fine while a model is still being shaped and the
  data is throwaway; never do it to a user's real data without asking.
- **A new entity beside the old one**, with a `REINDEX` migration in `./migrations` that
  copies the rows across (see below), which is the answer once data matters.

So the first shape an entity is pushed with is the cheap one to get right. Think the
fields through before the first push rather than reshaping afterwards.

## Using repositories

```typescript
import { Kinotic, Pageable } from '@kinotic-ai/core'
import { PersistencePlugin } from '@kinotic-ai/persistence'
import { PersonRepository } from '@my-app/domain'

Kinotic.use(PersistencePlugin)
await Kinotic.connect()   // server + credentials resolve from the environment

const people = new PersonRepository()

const saved = await people.save({ id: null, firstName: 'Jane', lastName: 'Doe', bio: '', age: 28 })
const page = await people.findAll(Pageable.create(0, 25))   // page.content, page.totalElements
const hits = await people.search('Jane', Pageable.create(0, 10))  // full-text query over the entity's fields
```

Repositories address the platform's `app-api` zone, which both application-scope and
organization-scope connections may reach — so they work from a published service, a
local script, and the browser alike. `Kinotic.use(PersistencePlugin)` adds the typed
`Kinotic.entities` accessor the docs' examples use; a generated repository works without it.

Full surface: `save`, `bulkSave`, `update` (partial — only fields present change; an
update of a missing entity upserts it unless the entity has `@Version`, which instead
makes the version mandatory or the update is rejected), `bulkUpdate`, `findById` (null when missing),
`findByIds`, `findAll`, `search`, `deleteById`, `deleteByQuery`, `count`,
`countByQuery`, `syncIndex`, plus `namedQuery` / `namedQueryPage` (what generated
`@Query` bodies call). Signatures in `references/decorators.md`.

`save` and `update` are read-your-write (the index refreshes on each call); **bulk**
writes are not — call `await people.syncIndex()` after `bulkSave`/`bulkUpdate` before
querying the results.

## Named queries

Custom queries go on the `<Entity>Repository` subclass (never the generated base) with
`@Query` and an empty body — `bun run generate` fills the implementation:

```typescript
import { Query } from '@kinotic-ai/persistence'
import type { Page, Pageable } from '@kinotic-ai/core'

// Row types are the app's own: an aggregate returns one row per group, shaped by its projection
export interface StatusCount { count: number }
export interface WriteCount { count: number }

export class OrderRepository extends BaseOrderRepository {

    @Query('SELECT * FROM Order WHERE status = :status ORDER BY createdAt DESC, id')
    findByStatus(status: string, pageable: Pageable): Promise<Page<Order>> {
        // Implementation is generated by the CLI
    }

    @Query('SELECT COUNT(*) AS count FROM Order WHERE status = :status')
    countByStatus(status: string): Promise<StatusCount[]> {
        // Implementation is generated by the CLI
    }

    @Query('UPDATE Order SET status = :status WHERE id = :id WITH REFRESH')
    updateStatus(id: string, status: string): Promise<WriteCount[]> {
        // Implementation is generated by the CLI
    }
}
```

A named query is one statement of the migration grammar, without the semicolon, naming the
repository's entity (not storage) with entity and field names spelled as the class spells
them. The method must return a `Promise`:

- `SELECT` returns the matching rows shaped as the entity; a method returning an array gets
  up to `LIMIT` rows (1000 when none), and one with a `pageable: Pageable` parameter returns
  a `Page`, with cursor paging ordered by the statement's `ORDER BY`.
- An aggregate — a `SELECT` calling a function (`COUNT(*)`, `SUM`, `AVG`, `MIN`, `MAX`,
  `PERCENTILE`, `HISTOGRAM`, …) or with `GROUP BY` — runs on Elasticsearch SQL and returns
  one row per group, shaped by the projection (`AS` names a column), never a bare number.
- `INSERT`, `UPDATE` and `DELETE` return one row `{ count }`; add `WITH REFRESH` when the
  next read must see the write.

Parameters bind by `:name`. Every query is confined to the caller's tenant, as the
repository's own methods are. A named query only works at runtime once its definition has
reached the server, which the next push does.
Docs: <https://kinotic.ai/apps/persistence/named-queries>.

## Migrations

A migration changes an entity's **data**, never its schema — the entity class is the
schema, and `kinotic sync` publishes every entity before it runs the migrations. Migrations
are SQL-like files in `./migrations`, named `V<N>__<description>.sql` (e.g.
`V2__seed_roles.sql`), applied in version order by the deployment's `kinotic sync` step and
recorded per project so they never re-run. An application's migration may use only the four
data statements — `INSERT`, `UPDATE`, `DELETE` and `REINDEX` (copy rows from one entity to
another) — each naming an entity of the application as the class spells it (`INSERT INTO
Person`, not a storage name); any other statement, or an unknown entity, fails the whole
run before anything executes, and a file with a syntax error applies nothing. Three rules
carry real weight:

- **Mappings are strict.** Storage mappings reject any field they do not know, failing
  the first save at runtime. A new field reaches storage by re-publishing the definition
  (additive updates apply automatically on the next push); a migration cannot add one.
- **Every inserted row states its id, and its tenant.** A migration cannot have an id
  generated for it: the `INSERT` must carry the entity's `@Id`/`@AutoGeneratedId` field, and
  on a `SHARED` entity its tenant field (the `@TenantId` field it declares, otherwise
  `tenantId`), because a migration runs for the organization, not for a tenant. The platform
  stores the row as the repository would, so it is found by id and by tenant afterwards;
  `ROUTING` and `DOCUMENT_ID` are refused, since both are derived. An `UPDATE` or `DELETE`
  reaches every tenant's rows unless its `WHERE` names the tenant field.
- **`WITH REFRESH` makes a write visible to the next read.** Composite fields take object
  and array literals, and an `UPDATE` with an object literal merges into the stored object,
  so naming one sub-field changes only that one and `null` clears one.

  ```sql
  INSERT INTO Person (id, tenantId, firstName, address)
      VALUES ('p-1', 'acme', 'Jane', { street: '1 Main St', city: 'Springfield' }) WITH REFRESH;
  UPDATE Person SET address = { city: 'Shelbyville' } WHERE id = 'p-1' WITH REFRESH;
  ```

Grammar: <https://kinotic.ai/apps/reference/migration-sql-grammar>.

## Multi-tenancy — deciding whether users share data

**Data is shared between all users by default.** If an app's users should each see only
their own rows, that takes two settings that must agree, and neither works alone:

| Application `tenantManagement` | Entity | Result |
|---|---|---|
| `TENANT_ADMINISTRATORS` | `MultiTenancyType.NONE` | One shared dataset — **every user sees every other user's rows** |
| `SYSTEM` | `MultiTenancyType.NONE` | Every user sees the rows — right for data the whole app shares, like a product catalog |
| `TENANT_ADMINISTRATORS` | `MultiTenancyType.SHARED` | Each user sees the rows of the tenant it was added to, shared with that tenant's other users |
| `SYSTEM` | `MultiTenancyType.SHARED` | Each user isolated in their own tenant |

Under `TENANT_ADMINISTRATORS` the organization creates each tenant — in the portal or
through `Tenant Service Create Tenant If Not Exist` — and every user of the application is
added to one, whose users share its rows.

Get this decided **before** the first users exist, because `SYSTEM` only assigns a
tenant of their own to users created while it is in force — existing users are never
moved, so they stay in the tenants they were added to beside the new users' own tenants.
It is set on the Application, not on the project: `Application Service Create Application
If Not Exist` takes it as an argument at creation, and afterwards it changes in the
portal (Application → **Settings**, the **Tenants** row of the General tab; `Application
Service Save` writes it too). The create-app skill picks it from the app's tenant
model, and the application's `tenantManagement` says which it is. Under `SYSTEM` each entity
chooses `SHARED` for rows private to each user and `NONE` for rows every user sees; under
`TENANT_ADMINISTRATORS`, `SHARED` for rows each tenant keeps to itself and `NONE` for rows
every tenant sees.

```typescript
import { Entity, AutoGeneratedId, NotNull, MultiTenancyType } from '@kinotic-ai/persistence'

@Entity(MultiTenancyType.SHARED)
export class Todo {
    @AutoGeneratedId
    id: string | null = null

    @NotNull
    title: string = ''
}
```

The generated repository is then transparently tenant-scoped: the tenant id comes from the
authenticated user and every query is filtered to it, so ordinary repository code needs no
tenant handling. The platform stores each row's tenant itself, so a `SHARED` entity needs no
tenant field to be isolated.

**`@TenantId` is optional for a user's client.** Declare a `@TenantId` field
(`tenantId: string = ''`) when the app's logic needs to read a row's tenant id on the
entity, or when a backend service must touch the entity (next paragraph). On a user's save
the field is filled with the user's tenant, and any other value is rejected.

**A backend service reaches a `SHARED` entity only by naming the tenant.** The tenant
comes off the authenticated participant, and only an APPLICATION-scope participant carries
one — the deployed runtime connects at organization scope (see the `services` skill), so a
`@Publish`ed service calling the tenant-scoped repository on a `SHARED` entity fails with
`Participant with a TenantId is required when MultiTenancyType is SHARED`. From
organization scope the entity must declare `@TenantId`: a save through the ordinary
repository then stores the row under the tenant the field names (and fails with
`Tenant Id field cannot be null` when it is blank), and reads go through the generated
`<Entity>AdminRepository`, whose every method takes a `TenantSelection` first — `['*']`
for all tenants, or a list of tenant ids — and which offers no save or update. A
tenant-bound user may select only its own tenant there, so the admin repository is for
services and scripts, not for the UI. Per-user reads and writes driven by the user belong
on a client connected as that user.

Docs: <https://kinotic.ai/apps/persistence/multi-tenancy>.
